## 1. Mettre en place une base de données relationnelle

### 1.1 Modélisation : les choix significatifs

MySQL est la base de référence de l'application : elle contient les utilisateurs, les menus, les plats, les allergènes, les commandes, l'historique de leurs statuts et les avis. Plutôt que de décrire chaque table, je présente les choix qui traduisent une règle fonctionnelle.

| Règle fonctionnelle | Choix de modélisation | Contrainte en base |
|---|---|---|
| Un plat peut figurer dans plusieurs menus ; un menu comprend plusieurs plats | Relation Many-to-Many `Menu` ↔ `Dish`, table de liaison `menu_dish` | Clé primaire composée `(menu_id, dish_id)` : une même association ne peut pas être enregistrée deux fois |
| Un allergène concerne plusieurs plats ; un plat peut contenir plusieurs allergènes | Many-to-Many `Dish` ↔ `Allergen`, table `dish_allergen` | Clé primaire composée `(dish_id, allergen_id)` |
| Supprimer un plat ne doit pas laisser d'associations orphelines | Clés étrangères des tables de liaison | `ON DELETE CASCADE` sur `menu_dish` et `dish_allergen` |
| Toute commande est passée par un client connecté | Many-to-One `CustomerOrder` → `User` | `user_id NOT NULL` + clé étrangère (rendu obligatoire par la migration `Version20261021103957`) |
| Une commande porte sur un menu précis | Many-to-One `CustomerOrder` → `Menu` | `menu_id NOT NULL` + clé étrangère |
| On doit pouvoir retracer le suivi d'une commande | One-to-Many `CustomerOrder` → `OrderStatusHistory` | `customer_order_id NOT NULL` + clé étrangère |
| Un compte est identifié par son adresse e-mail | Identifiant de connexion | Index `UNIQUE` sur `user.email` |

**Copie des coordonnées et des montants dans la commande.** `CustomerOrder` duplique volontairement le nom, l'e-mail, le téléphone et l'adresse de prestation, ainsi que `menu_price`, `delivery_price`, `discount_amount` et `total_price`. Ce choix conserve l'état de la commande au moment où elle a été passée : si le client modifie son profil ou si le tarif d'un menu change, l'historique reste exact. C'est une dénormalisation assumée, au service d'une règle métier.

**Statut courant et historique.** La colonne `status` de `customer_order` donne le statut courant, utilisé pour les filtres de l'espace employé. La table `order_status_history` conserve chaque changement avec sa date. La clé étrangère garantit qu'une entrée d'historique appartient à une commande ; en revanche, la présence d'un premier statut à la création est assurée par l'application (voir 2.1), pas par la base.

**Annulation.** Les colonnes facultatives `cancel_reason` et `contact_mode` enregistrent le motif d'une annulation et le moyen par lequel le client a été contacté.

### 1.2 Cohérence des données : types, contraintes, nommage

- **Montants** : `DECIMAL(10,2)`, manipulés comme chaînes dans les entités. Un type décimal exact évite les erreurs d'arrondi des nombres à virgule flottante sur des prix.
- **Téléphone et code postal** : `VARCHAR`. Ce sont des identifiants, pas des quantités ; un type numérique supprimerait par exemple le zéro initial de `06…`.
- **Dates** : `DATE` pour le jour de prestation, `TIME` pour l'heure de livraison, `DATETIME` pour les horodatages (`created_at`, `changed_at`).
- **Nullabilité** : obligatoire pour les informations indispensables à une commande ; facultative pour `cancel_reason`, `contact_mode`, `updated_at` ou les champs de profil non exigés à l'inscription.
- **Nommage** : entités et propriétés en `camelCase` côté PHP (`deliveryDate`), tables et colonnes en `snake_case` côté MySQL (`delivery_date`), conversion assurée par Doctrine. Les clés étrangères suivent le format `<entité>_id`.
- **Moteur InnoDB** : nécessaire aux clés étrangères et aux transactions.

Extrait réel de `src/Entity/CustomerOrder.php` :

```php
#[ORM\Column(type: Types::DECIMAL, precision: 10, scale: 2)]
private ?string $totalPrice = null;

#[ORM\ManyToOne(inversedBy: 'customerOrders')]
#[ORM\JoinColumn(nullable: false)]
private ?Menu $menu = null;
```

### 1.3 Création et évolution du schéma : migrations Doctrine

Les **migrations Doctrine pilotent l'évolution de la base**. Les attributs `#[ORM\...]` des entités décrivent le schéma attendu ; Doctrine compare ce mapping avec la base et génère une migration versionnée, que je relis avant de l'appliquer. La table `doctrine_migration_versions` enregistre les migrations déjà exécutées.

Exemple réel : rendre obligatoire le rattachement d'une commande à un utilisateur.

1. Vérification préalable qu'aucune commande existante ne serait bloquée :

```sql
SELECT id, status, customer_email FROM customer_order WHERE user_id IS NULL;
-- Résultat : aucune ligne
```

2. Modification du mapping dans `CustomerOrder.php` :

```php
#[ORM\ManyToOne(inversedBy: 'customerOrders')]
#[ORM\JoinColumn(nullable: false)]
private ?User $user = null;
```

3. Génération, relecture puis application de la migration (le projet tourne sous Docker ; MakerBundle n'est disponible qu'en environnement `dev`) :

```bash
docker compose exec php php bin/console make:migration --env=dev
docker compose exec php php bin/console doctrine:migrations:migrate --env=dev
```

Migration générée `migrations/Version20261021103957.php` :

```php
public function up(Schema $schema): void
{
    $this->addSql('ALTER TABLE customer_order CHANGE user_id user_id INT NOT NULL');
}

public function down(Schema $schema): void
{
    $this->addSql('ALTER TABLE customer_order CHANGE user_id user_id INT DEFAULT NULL');
}
```

4. Vérification dans phpMyAdmin :

```sql
SHOW COLUMNS FROM customer_order LIKE 'user_id';
-- Null = NO
```

**Rôle de `schema.sql`.** Le fichier `schema.sql` est un **export de la structure** réalisé avec phpMyAdmin (« Exporter » → « Structure uniquement ») après application des migrations. Il sert de document lisible et d'annexe ; il n'est pas utilisé pour faire évoluer la base. En cas d'écart, ce sont les migrations qui font foi.

> **Preuve — Figure 18 :** la migration `Version20261021103957`, le résultat de `doctrine:migrations:migrate`, et un extrait de `schema.sql` montrant `customer_order`, `order_status_history` et leurs clés :


Choix techniques du script :

```sql
START TRANSACTION;
INSERT INTO menu (title, ..., created_at) VALUES ('Menu végétal convivial', ..., @seed_now);
SET @seed_menu_1 = LAST_INSERT_ID();
INSERT INTO menu_dish (menu_id, dish_id) VALUES (@seed_menu_1, @seed_dish_1_1);

COMMIT;
```

- Une **transaction** : en cas d'erreur, aucun ajout partiel n'est conservé.
- Des **variables MySQL** (`@seed_...`) mémorisent les identifiants générés par `LAST_INSERT_ID()`, au lieu de supposer des identifiants fixes alors que la base contient déjà des données.

### 1.5 Sécurité et confidentialité

**Mesures en place**

- **Mots de passe hachés** : `password_hashers: 'auto'` dans `config/packages/security.yaml` (lignes 2-3) ; aucun mot de passe en clair en base, y compris dans les fixtures.
- **Réinitialisation de mot de passe** : la table `reset_password_request` stocke un jeton haché (`hashed_token`) avec une date d'expiration.
- **Accès par rôle** : hiérarchie `ROLE_ADMIN` → `ROLE_EMPLOYEE` → `ROLE_USER` et règles `access_control` sur `/admin`, `/employe` et `/compte` (lignes 5-7 et 37-41).
- **Minimisation dans MongoDB** : les statistiques ne contiennent que des identifiants de menu et de commande, le titre du menu, le mois et des compteurs. Aucune donnée personnelle n'y est copiée.
- **Jeu d'essai fictif** et sauvegarde contenant des données réelles conservée **hors du dépôt Git**.

**Limites identifiées (environnement de développement)**

- L'application se connecte à MySQL avec le compte `root` (`DATABASE_URL`), dont le mot de passe par défaut figure dans `compose.yaml`. En production, il faudrait un compte dédié limité à la base `vite_gourmand` et aux droits `SELECT`, `INSERT`, `UPDATE`, `DELETE`, et un compte distinct pour les migrations, avec des secrets stockés hors du dépôt.
- MongoDB fonctionne sans authentification et son port est publié sur la machine (`27018`). En production : authentification activée et port non exposé.
- **RGPD** : la conservation des coordonnées dans les commandes est justifiée par le suivi de la prestation, mais elle ne doit pas être illimitée. Une durée de conservation reste à définir, suivie d'une suppression ou d'une anonymisation.

### 1.6 Sauvegarde et restauration

**Réalisé** : export complet de la base (structure et données) depuis phpMyAdmin avant l'import du jeu d'essai (« Exporter » → « Personnalisée » → Structure + Données), fichier conservé hors du dépôt.

**Non réalisé à ce jour** : test de restauration et automatisation des sauvegardes.

**Stratégie proposée**

- **MySQL** est la seule base à sauvegarder : elle contient les données de référence.
- **MongoDB** ne contient que des statistiques dérivées : elles se reconstruisent depuis MySQL avec `app:stats:rebuild`. Sa sauvegarde n'est donc pas indispensable.
- En production : sauvegarde quotidienne, copie stockée hors du serveur, accès restreint, conservation limitée (par exemple 7 sauvegardes quotidiennes et 4 hebdomadaires) et test de restauration régulier. Avec une sauvegarde quotidienne, une panne peut faire perdre les commandes passées depuis la dernière sauvegarde : c'est le compromis à assumer ou à réduire.

**Vérification d'une restauration (procédure à tester)**

1. Créer une base distincte `vite_gourmand_restore` et y importer la sauvegarde via phpMyAdmin, sans toucher à la base principale.
2. Comparer les deux bases avec la même requête :

```sql
SELECT status, COUNT(*) AS nb, SUM(total_price) AS montant
FROM customer_order
GROUP BY status
ORDER BY status;
```

3. Vérifier le nombre d'utilisateurs, de menus et d'entrées d'historique.

## 2. Développer des composants d'accès aux données SQL et NoSQL

### 2.1 Accès SQL avec Doctrine

**Lecture : repositories.** Chaque entité possède un repository (`MenuRepository`, `CustomerOrderRepository`, `ReviewRepository`…). Les requêtes simples utilisent les méthodes fournies par Doctrine, comme `findBy()` ; les requêtes spécifiques sont regroupées dans des méthodes dédiées.

`MenuRepository::findByFilters()` (`src/Repository/MenuRepository.php`, lignes 20-45) construit la requête selon les filtres reçus :

```php
if ($minPrice !== null) {
    $qb->andWhere('m.basePrice >= :minPrice')->setParameter('minPrice', $minPrice);
}
if ($theme) {
    $qb->andWhere('m.theme = :theme')->setParameter('theme', $theme);
}
```

Chaque valeur est liée par `setParameter()` : elle n'est jamais concaténée dans la requête, ce qui protège contre l'injection SQL.

**Conformité fonctionnelle.** Ce repository répond aux filtres exigés sur la page des menus : prix minimum et maximum, thème, régime et nombre minimum de personnes. La route `GET /api/menus` (`MenuController.php`, lignes 33-61) convertit les paramètres reçus (`(float)`, `(int)`, valeur vide → `null`), appelle le repository et renvoie du JSON, que la page exploite sans rechargement.

**Écriture : EntityManager.** La création d'une commande (`OrderController.php`, lignes 77-86) enregistre la commande et son premier statut dans un même `flush()`, que Doctrine exécute dans une transaction SQL :

```php
$history = new OrderStatusHistory();
$history->setStatus('en_attente');
$history->setChangedAt($now);
$order->addOrderStatusHistory($history);

$entityManager->persist($order);
$entityManager->persist($history);
$entityManager->flush();
```

Le changement de statut par un employé suit le même principe : nouveau statut et entrée d'historique enregistrés ensemble, avant tout effet externe (e-mail, statistiques).

### 2.2 Validation des entrées avant les opérations en base

- **Formulaire de commande** (`CustomerOrderType.php`) : `NotBlank` et `Length` alignés sur la taille des colonnes (par exemple 100 caractères pour le prénom, 255 pour l'adresse), `Email`, expression régulière sur le téléphone (lignes 37-41), date de prestation au plus tôt aujourd'hui, et `GreaterThanOrEqual` sur le nombre de personnes, avec le minimum du menu (lignes 66-75).
- **Montants calculés côté serveur** : le navigateur ne transmet jamais le prix. Les montants sont calculés par `OrderQuoteCalculator` après validation du formulaire (`OrderController.php`, lignes 55-58).
- **Simulation de prix** : contrôle du jeton CSRF, des longueurs et du nombre de personnes avec `filter_var(..., FILTER_VALIDATE_INT)` (lignes 177-207) ; en cas d'erreur, réponse 422 sans création de commande.
- **Changement de statut** : jeton CSRF vérifié et statut contrôlé dans une liste blanche des 8 valeurs autorisées (`EmployeeSpaceController::updateStatus()`).

### 2.3 Intégrité et confidentialité

- `#[IsGranted]` sur les contrôleurs employé et administrateur, `denyAccessUnlessGranted('ROLE_USER')` pour commander.
- Commande rattachée à l'utilisateur connecté côté serveur (`$order->setUser($user)`), et non à une valeur envoyée par le formulaire.
- Jetons CSRF sur les formulaires de commande, de changement de statut et de modération des avis.
- Contraintes de la base (clés étrangères, `NOT NULL`, `UNIQUE`) en dernier rempart.

**Limite connue.** Les transitions entre statuts ne sont pas encore contrôlées : un employé peut sélectionner n'importe quel statut de la liste, y compris faire revenir une commande `terminee` à un statut antérieur. Le code le signale (`// Le contrôle des transitions métier reste à ajouter ici.`). Cela affecte les statistiques : `markOrderCompleted()` ne décrémente rien si une commande quitte `terminee`. La correction prévue consiste à rendre `terminee` et `annulee` définitifs et à n'autoriser que les transitions du cycle de commande, avec un test associé.

### 2.4 Accès NoSQL : pourquoi MongoDB pour les statistiques

**Rôle.** MongoDB contient une **projection statistique** des commandes : des compteurs déjà calculés, consultés par l'espace administrateur (`/admin/stats`). MySQL reste l'unique source de vérité ; MongoDB peut être effacé et reconstruit.

**Bénéfice concret.** La page de statistiques lit directement un document par menu (`menu_stats`) et un document par menu et par mois (`menu_monthly_stats`), sans regrouper ni additionner l'ensemble des commandes à chaque affichage. Chaque nouvelle commande met à jour ces compteurs par une opération atomique sur un seul document :

```php
$this->monthlyStats->updateOne(
    ['menuId' => $menu->getId(), 'month' => $month],
    [
        '$setOnInsert' => ['menuId' => $menu->getId(), 'month' => $month],
        '$inc' => ['orders' => 1],
    ],
    ['upsert' => true]
);
```

`upsert` crée le document s'il n'existe pas ; `$inc` incrémente le compteur sans lecture préalable. La séparation isole aussi les traitements statistiques des données métier : une indisponibilité de MongoDB n'empêche pas de passer une commande.

**Ce bénéfice reste un choix d'architecture.** Avec les volumes du projet, MySQL pourrait calculer les mêmes indicateurs avec une requête `GROUP BY`. Je n'ai pas mesuré de gain de performance et je ne présente donc pas MongoDB comme indispensable.

**Coût en complexité.** Deux bases à installer, sécuriser et superviser ; une bibliothèque d'accès supplémentaire (`mongodb/mongodb`, bibliothèque officielle, distincte de Doctrine) ; des statistiques qui peuvent être temporairement décalées par rapport à MySQL ; une commande de reconstruction à maintenir.

**Service dédié.** `MongoStatsService` centralise tout l'accès à MongoDB : les contrôleurs ne manipulent jamais les collections directement. Quatre collections :

| Collection | Contenu |
|---|---|
| `menu_stats` | Par menu : `totalOrders`, `completedOrders`, `completedRevenue` |
| `menu_monthly_stats` | Par menu et par mois : `orders`, `completedOrders`, `completedRevenue` |
| `processed_order_stats` | Identifiants des commandes déjà comptées |
| `completed_order_stats` | Identifiants des commandes déjà comptées comme terminées |

Des **index uniques** sur `orderId` empêchent de compter deux fois la même commande ; un index unique sur `(menuId, month)` garantit un seul document par menu et par mois (lignes 40-62).

**Indicateurs.** `totalOrders` compte les commandes enregistrées ; `completedOrders` et `completedRevenue` ne concernent que les commandes au statut `terminee`. `completedRevenue` est la somme des montants des prestations terminées : l'application n'enregistre pas de paiement, ce n'est donc pas un montant encaissé. Les statistiques mensuelles sont rattachées au **mois de création** de la commande. L'administrateur peut filtrer par menu et par période (`getRevenueByMenuAndPeriod()`).

### 2.5 Gestion des exceptions et des échecs

| Situation | Comportement actuel |
|---|---|
| Calcul du prix impossible (adresse, service de géolocalisation) | Erreur journalisée, message dans le formulaire, **aucune commande créée** (`OrderController.php`, lignes 56-62) |
| Échec de l'enregistrement MySQL | Erreur journalisée ; le client est redirigé vers son espace avec un message lui demandant de vérifier avant toute nouvelle tentative, pour éviter un doublon (lignes 83-109) |
| MongoDB indisponible à la création ou à la clôture d'une commande | La commande est déjà enregistrée dans MySQL ; l'erreur est journalisée avec l'identifiant de la commande, sans bloquer l'utilisateur (lignes 112-122 et `EmployeeSpaceController`) |
| Échec d'envoi d'e-mail | Statut ou commande conservés, message d'avertissement, erreur journalisée |
| Simulation de prix impossible | Réponse JSON 503 avec un message explicite |

Le principe est constant : **enregistrer d'abord dans MySQL, puis déclencher les effets secondaires**, dont l'échec est journalisé sans annuler l'opération principale.

**Limites identifiées**

- Dans `incrementOrderStats()` et `markOrderCompleted()`, le marqueur « déjà traité » est inséré **avant** la mise à jour des compteurs. Si MongoDB échoue entre ces deux écritures, la commande est marquée sans être entièrement comptée. De plus, toute `BulkWriteException` est interprétée comme un doublon (lignes 79-82), alors qu'elle peut avoir une autre cause. Amélioration prévue : ne traiter comme doublon que l'erreur de clé dupliquée (code 11000) et journaliser les autres.
- La page `/admin/stats` n'intercepte pas encore les erreurs de connexion à MongoDB : si MongoDB est arrêté, l'administrateur obtient une page d'erreur au lieu d'un message explicite.

**Reprise : reconstruction depuis MySQL.** La commande `app:stats:rebuild` (`RebuildOrderStatsCommand.php`) demande une confirmation, vide les quatre collections, relit toutes les commandes MySQL et recalcule les statistiques ; seules les commandes au statut `terminee` alimentent les indicateurs de prestations terminées.

```bash
docker compose exec php php bin/console app:stats:rebuild --env=dev
```

Après l'import du jeu d'essai, la reconstruction a été exécutée avec succès : « Statistiques reconstruites à partir de 25 commande(s) ». C'est une reprise manuelle, à lancer sans modification concurrente des commandes ; ce n'est pas une sauvegarde.

**Vérifier la cohérence entre les deux bases.** Même indicateur des deux côtés :

```sql
-- MySQL (phpMyAdmin)
SELECT menu_id,
       COUNT(*) AS total_orders,
       SUM(status = 'terminee') AS completed_orders,
       SUM(CASE WHEN status = 'terminee' THEN total_price ELSE 0 END) AS completed_revenue
FROM customer_order
GROUP BY menu_id
ORDER BY menu_id;
```

```bash
# MongoDB
docker compose exec mongo mongosh vite_gourmand --eval 'db.menu_stats.find({}, {_id:0}).sort({menuId:1}).toArray()'
```

Les valeurs doivent être identiques pour chaque menu. En cas d'écart, la reconstruction rétablit la cohérence.
